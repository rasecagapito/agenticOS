CAPÍTULO 01

As 5 camadas do sistema

Todo projeto Agentic OS é construído sobre cinco camadas de arquivos. Juntas, transformam qualquer pasta num ambiente onde uma IA trabalha com memória e autonomia entre sessões.

CAMADA 01
◈
CLAUDE.md / AGENTS.md

Identity — o orquestrador: quem é o projeto, as regras, os workers e o protocolo de arranque.

CAMADA 02
❖
context/

Knowledge — conhecimento modular por tema (ou por módulo de código). Carregado sob demanda.

CAMADA 03
◐
memory/

Memory — history/ (logs de sessão) + learnings/ (aprendizados). Cresce a cada /wrapup.

CAMADA 04
⬡
workers/

Workers — especialistas: Papel · Função · Contexto a Carregar · Schema de Saída · Restrições.

CAMADA 05
◉
automation/

Automation — evaluation.json (gates de qualidade) + guardrails.md (ações que exigem humano).

O coração do sistema é uma só ideia: fontes únicas. Cada lógica existe uma vez — comandos são wrappers de automation/procedures/; cada cérebro existe uma vez — os outros arquivos de IA são ponteiros @import; o progresso existe uma vez — tasks.md; o estado dinâmico existe uma vez — memory/handoff.md. Duplicação = drift = delírio.

CAPÍTULO 03

O ciclo de mudança

Toda feature, correção ou reorganização é uma mudança: uma pasta em changes/<nome>/ que captura porquê, como e passos antes de mexer no código. O ciclo tem três tempos:

①
/propose add-dark-mode

Cria a mudança: proposal.md (porquê/escopo/abordagem) + tasks.md (checklist) + design.md se não-trivial. Em projeto modular, prefixa o módulo.

→
②
/worker developer

Ativa o especialista com contexto carregado e executa tarefa a tarefa. Cada fechamento marca [x] e grava o handoff incremental.

→
③
/wrapup

Consolida: history + learnings, sugere deltas em context/ (confirmados item a item), arquiva a mudança, finaliza o handoff.

Regra de Ouro: o sistema só cria. Nunca move, renomeia ou apaga arquivos existentes sem mudança aprovada (/propose + gate humano).
CAPÍTULO 04

Os 7 comandos — referência

No Claude Code são slash commands; em Codex, Gemini e outras IAs, pede-se em linguagem natural e a IA lê o procedimento provider-neutro equivalente. A lógica vive uma vez em automation/procedures/.

/propose <nome>NL: “faz o propose add-login”
Cria uma mudança estruturada. Nome kebab-case; ponte para specs de brainstorming; projeto modular pergunta o módulo e prefixa. Sem argumento, lista mudanças ativas.$ /propose add-dark-mode → changes/add-dark-mode/ criada: proposal.md + tasks.md (6 tarefas)
/worker [nome]NL: “ativa o worker developer”
Ativa o especialista e executa a mudança ativa. Carrega só o contexto do worker, retoma no cursor (1ª tarefa [ ]), respeita o Limite aprovado com Orquestração, grava handoff + sha a cada tarefa fechada. Sem argumento, lista workers.Worker developer ativo. Contexto: [arquitetura, produto]. Retomando na tarefa 3 (limite aprovado: 5).
/wrapupNL: “faz o wrapup”
Consolida a sessão. Registro em memory/history/, aprendizados em memory/learnings/, deltas de context/ confirmados um a um, arquivamento da mudança, fechamento do handoff. Exclusivo da coordenação quando a Orquestração está ativa.Sessão consolidada. Registro: 2026-08-05-1430-sessao.md Handoff atualizado. Mudança arquivada.
/statusNL: “mostra o status”
Fotografia do projeto: branch, últimos commits, último provedor (handoff), mudança ativa + cursor, estado da Orquestração (limite/executor/aguardando?), fase e top 3 pendências — em tabela compacta.
/conformNL: “corre o conform”
Loop de conformidade A/B. Sem argumento = só auditar (dry-run). Com aprovação: Agente A audita (read-only) → gate humano → Agente B aplica só o aprovado → A re-audita o disco, até PASS (máx. 3 ciclos). Ver capítulo 07.
/handoffNL: “lê/atualiza o handoff”
Estado vivo multi-provedor. Sem argumento = LER o estado atual; com “grava” = GRAVAR o estado em memory/handoff.md. É o que permite a outra IA continuar exatamente onde esta parou. Ver capítulo 05.$ /handoff Último provedor: Codex · 2026-08-05 14:12 · cursor: tarefa 3
/structureNL: “audita a estrutura”
Motor de Estrutura da Aplicação. Monta/audita a estrutura do código-fonte por perfil (next-app · generico): marcador de perfil, AGENTS.md canônico, emissão de regras para Cursor/Copilot a partir da fonte única, auditoria S1–S7/DS1–DS2. Projeto implantado = Tier 0 (código intocado).
CAPÍTULO 05

O handoff — continuidade exata

Uma camada resolve dois problemas: cada IA lê um arquivo diferente → fonte única + ponteiros; não há continuidade → o handoff. Este é o segundo arquivo mais lido de todo o sistema — por isso tem teto rígido de 20 linhas.

memory/handoff.mdestado vivo · ≤ 20 linhas
# Handoff — estado vivo da sessão
> Lê isto PRIMEIRO. Validação: mudança ativa não existe,
> ou cursor ≠ 1ª [ ] em tasks.md, ou cursor além do Limite
> aprovado → parar e perguntar. Não improvisar.

## Sessão
- IA: Codex · Quando: 2026-08-05 14:12

## Orquestração
- Orquestrador: humano (gate final) · Coordenação: Claude
- Limite aprovado: tarefa 4 de tasks.md · Executor: Codex
- Aprovado por humano em: 2026-08-05 11:40
- Âncora: commit a1b2c3d da última aprovação

## Mudança ativa
- Pasta: changes/add-dark-mode/
- Cursor: 1ª [ ] em tasks.md, ≤ Limite (derivar — não copiar)

## Narrativa (1 linha por campo)
- Feito: toggle + persistência · Decidido: localStorage
- Gotchas: — · Próxima intenção: fechar tarefa 4
01
Cursor derivado

A próxima tarefa é sempre a 1ª [ ] de tasks.md. Nunca copiar a lista para o handoff — duas fontes de verdade é o começo do delírio (D3).

02
Estado dinâmico único (D6)

Sessão, cursor e próximo passo vivem só aqui. O cérebro guarda apenas estado estático (fase do projeto). Zero dupla escrita.

03
Âncora git

Cada tarefa fechada grava commit <sha>. “O que aconteceu desde então” deriva de git diff sha..HEAD — não de prosa.

04
Teto rígido

≤ 20 linhas. Narrativa de 1 linha por campo. Substituir, nunca acumular — crescimento aqui é custo recorrente em toda sessão.

05
Validação co-localizada

A instrução de arranque vive no próprio header — a IA já vai ler o arquivo mesmo. Custo zero no cérebro; conflito → parar e perguntar.

06
À prova de crash

Grava ao fechar cada tarefa, não só no wrapup. Sessão morreu? A próxima IA retoma igual via changes/ + handoff.

Protocolo de arranque — toda IA, sempre
  1. 1 Ler handoff.md + validar
  2. 2 Abrir a mudança ativa
  3. 3 Retomar na 1ª [ ] (≤ limite)
  4. 4 Carregar só o context/ relevante
Fonte única + ponteiros: AGENTS.md é o cérebro canônico (Codex lê nativamente); CLAUDE.md e GEMINI.md são 7 linhas de @import. CI pointer-check garante: todo ponteiro importa o canônico e o canônico nunca está vazio.
CAPÍTULO 06

Orquestração — o humano é o gate final

Com várias IAs no mesmo projeto, o modo seguro não é “cada uma avança sozinha”. É uma coordenação que propõe, executores que cumprem lotes aprovados, e o humano com a palavra final. Ativa quando o handoff traz a seção ## Orquestração — sem ela, vale o modo livre.

Como ativar a orquestração
O interruptor é uma só coisa: a seção ## Orquestração dentro de memory/handoff.md. Seção presente = ativa · ausente = modo livre (comportamento clássico).
AProjeto novo

Monte com o template D (ou peça à skill o modo multi-provedor): o handoff já nasce com a seção. É o padrão em projeto novo — para modo livre, remova a seção.

BProjeto existente

Peça à skill: “adapta este projeto ao Agentic OS com a camada multi-provedor e orquestração”. Ela cria handoff + seção sem tocar no que já existe.

CManual

Num projeto já multi-provedor: copie o bloco ## Orquestração (do capítulo 05) para o seu handoff. Para desativar: apague a seção.

Ritual de primeiro uso
  1. 1 Preencha Coordenação (quem propõe/revê) no handoff
  2. 2 Coordenação roda /propose e propõe o 1º lote (3–5 tarefas)
  3. 3 Humano aprova → registra Aprovado por humano em: … + limite + âncora
  4. 4 Executor assume o lote; o ciclo passa a correr sozinho até cada novo gate
Orquestrador final

HUMANO

Aprova lotes antes da execução e decide avançar o limite, trocar o executor ou bloquear. Nada além do limite vigente acontece sem ele.

Regras invioláveis da orquestração

1. O Limite aprovado só avança com aprovação humana registrada no handoff — tarefa [x] além do limite = DRIFT (D7), auditável pelo /conform.
2. Executor nunca improvisa além do lote; gotcha → parar e registrar, nunca contornar.
3. /propose e /wrapup são da coordenação; executores só executam tarefas aprovadas.
4. A seção de Orquestração nunca copia a lista de tarefas — só limite (índice), executor e âncora.
5. Revisão de lote sempre via git diff desde a âncora — a âncora é a fonte, não a memória da IA.
6. Duas IAs simultâneas são serializadas pela fronteira: um lote por executor, intervalos nunca duplicados.

Por que isso economiza tokens

Sem retrabalhoDuas IAs refazendo a mesma tarefa é o pior cenário de custo possível. A fronteira custa ~12 tokens por sessão para impedir isso.
Revisão barataA coordenação não relê o projeto inteiro: o git diff desde a âncora resume o lote em segundos.
Estado enxutoHandoff ≤ 20 linhas e cérebro ≤ 150: os arquivos quentes de toda sessão permanecem mínimos, sempre.
CAPÍTULO 07

Conformidade — loop A/B

O padrão não é um conselho: é uma spec verificável. O loop A/B constrói e corrige o projeto até ele bater exatamente o desenho — com gate humano entre a auditoria e a execução.

A

Auditoria read-only. Agente A compara o disco com a SPEC: cada item vira CONFORME | FALTA | DRIFT + instruction set preciso.

⬥

Gate humano. Aprova tudo ou item a item. Em projeto existente, default conservador: mover/apagar exige aprovação explícita.

B

Executor. Aplica exatamente o aprovado — sem scope creep. No Claude Code, A e B podem ser subagentes reais.

A²

Re-auditoria do disco (não da narrativa). PASS → sucesso. Senão → re-instrui B com o delta. Máx. 3 ciclos, depois escala.

CAPÍTULO 08

Motor de estrutura

Enquanto o resto organiza o cérebro, o /structure organiza e audita o código-fonte: perfis (next-app · generico), regras emitidas da fonte única para Cursor e Copilot, e uma escada de migração que protege produção.

DEFAULT
0

Só convenções

AGENTS.md + regras com escopo. Código intocado; tudo que é novo já nasce no formato. ~90% do valor, 0% de risco.

1

Auditoria

Agente A mapeia a distância até o perfil-alvo: relatório de gap + backlog priorizado. Nada é tocado.

2

Migração incremental

Um módulo por vez, via /propose migrate-*. Reference-safe, com gate de build: vermelho → rollback.

3

Reorg completo

Só projetos pequenos/pouco críticos ou sob pedido explícito, com git limpo e testes decentes.

Projeto já implantado = Tier 0 por padrão. Migração real (Tier 2) é opt-in, módulo a módulo, sempre protegida pelo gate de build (DS2). Regras verificáveis S1–S7 + DS1–DS2 em docs/STRUCTURE-SPEC.md.
CAPÍTULO 09

A lei do sistema — D1–D7

Sete regras anti-drift invioláveis: qualquer uma força FAIL na auditoria. As marcadas em âmbar chegaram na v1.4.0 com o hardening do handoff.

D1

Sem commands/ na raiz duplicando .claude/commands/ + procedures/ — três fontes da mesma lógica é drift garantido.

D2

Ponteiro nunca duplica o cérebro. CLAUDE.md/GEMINI.md só apontam; o conteúdo vive no canônico.

D3

Handoff nunca copia a lista de tarefas. O cursor é derivado; tasks.md é a única verdade do progresso.

D4

evaluation.json reflete os provedores reais — não só um.

D5

Uma só fonte por lógica de comando. Se existe procedures/x.md, o wrapper não reimplementa.

D6

Estado dinâmico único. Sessão/cursor/próximo passo vivem só em memory/handoff.md; o cérebro guarda só o estático.

D7

Fronteira de aprovação. Tarefa [x] além do Limite aprovado sem gate humano = DRIFT.

Orçamentos — concisão é gate, não conselho

Gotchas do operador

A IA recomeçou do zero
Não leu o handoff no arranque. Verifique o protocolo de arranque no cérebro e rode scripts/check-pointers.sh: se o ponteiro não importa o canônico, a IA só vê 7 linhas e trabalha “cega”.
Narrativa contradiz a tasks.md
Alguém editou tarefas sem respeitar o cursor derivado. Conflito de arranque → a IA deve parar e perguntar. Resolva na tasks.md — ela é a fonte única do progresso.
Executor avançou além do limite
DRIFT D7. Reverta o trabalho ou formalize retroativamente — apenas com aprovação humana registrada no handoff.
Sessão morreu sem /wrapup
Sem drama: o worker grava o handoff incrementalmente a cada tarefa fechada (com sha). A próxima IA retoma pelo cursor + git log desde a âncora e registra o gotcha.
Windows sem Git Bash
Use a variante PowerShell do Stop hook — a skill detecta o SO e instala a correta (nunca as duas).
Credenciais
Sempre variáveis de ambiente. Nunca em context/, memory/ ou nos arquivos cérebro.
